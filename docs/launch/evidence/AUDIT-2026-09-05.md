# SableStone launch audit — 5 September 2026

Commit: `15cf22272c1189b2b9a7fd881e9649b3b970cc1e`.

Verdict: **NO-GO, including when incorporation, banking, hosting and API credentials are assumed complete.** There are demonstrated software failures on the first-trade money path and additional source-supported breaks in continuing autonomous operation.

This was an audit, not an implementation session. No application source, live flag, GitHub Actions configuration or provider account was changed. No external commercial message, payment, production deployment or paid API operation was performed.

## What the evidence proves

- All 61 forward migrations applied to a new, disposable PostgreSQL 16 database.
- PostgreSQL parsed/analyzed 441 static production SQL statements: 439 passed; two failed against the actual migrated schema. This is not a claim that the 439 statements executed successfully with business data.
- 413 literal query-parameter arrays were checked: one has a 14-placeholder/13-parameter mismatch.
- The settlement query was submitted and reproduced PostgreSQL `08P01` before any insert.
- The real supplier-payout dispatcher was invoked on the disposable database and reproduced PostgreSQL `42P01` before any provider call.
- The production payment inbox handler was invoked with synthetic native-shaped Razorpay payment data: numeric timestamp rejected; substituting an ISO timestamp then exposed the paise/rupee mismatch. This is a local contract probe, not a real provider call.
- A root build with the undeclared global compiler excluded from PATH failed with exit 127, `tsc: not found`.
- Fresh `npm run check` and `npm run build` passed with the developer machine's existing global compiler. The runtime probes were repeated against that freshly compiled output and reproduced the failures listed above.
- The existing signed local verification report and release signature both verify against current covered source: seven recorded commands, 347 source files, live flags disabled. Authenticity of that report does not establish integrated production correctness.

Reproduction script: [audit-probes.mjs](/home/virk/Projects/B2B/sablestone-brokerage/docs/launch/evidence/audit-probes.mjs). It requires a disposable migrated database in `AUDIT_DATABASE_URL`, the repository as working directory, installed dependencies and current compiled output. Do not point this probe at production.

## Demonstrated money-path failures

### 1. P0 — Economic evaluation cannot finish

[opportunity_priority.ts:34](/home/virk/Projects/B2B/sablestone-brokerage/src/runtime/opportunity_priority.ts:34) selects `ht.created_at` from `trades`. That column does not exist after all migrations; the table has `updated_at`.

Actual database error: `42703: column ht.created_at does not exist`.

This is not just a broken dashboard score. [economic_jobs.ts:545](/home/virk/Projects/B2B/sablestone-brokerage/src/runtime/economic_jobs.ts:545) calls `refreshMatchPriority` inside the transaction that creates pricing/negotiation and the `MATCH_EXECUTABLE` outbox event. Once an executable match reaches that call, the error rolls the transaction back. Acceptance also calls this priority function.

Required proof after correction: a production economic-evaluation transaction commits pricing, negotiation and its outbox event on real PostgreSQL, including empty-history and historical-trade cases.

### 2. P0 — Settlement instruction insertion is unexecutable

[stage_handlers.ts:866](/home/virk/Projects/B2B/sablestone-brokerage/src/runtime/stage_handlers.ts:866) has 14 SQL parameters but supplies 13 values. The selected adapter/provider value is missing before `facts.product_family`, shifting the remaining fields.

Actual database error: `08P01: bind message supplies 13 parameters, but prepared statement "" requires 14`.

This fails before an instruction can be acknowledged, funded or used to secure entitlement.

Required proof: exact provider, commodity, currency, amounts, expiry, snapshot and waterfall digest persisted by the real settlement activity, then both counterparty acceptances and provider creation.

### 3. P0 — Supplier payout dispatcher cannot run

[supplier_payouts.ts:16](/home/virk/Projects/B2B/sablestone-brokerage/src/runtime/supplier_payouts.ts:16) references UPDATE target alias `p` inside the JOIN condition of its FROM clause where PostgreSQL cannot access it.

Actual dispatcher error: `42P01: invalid reference to FROM-clause entry for table "p"`.

The failure happens even on an empty database, before adapter release. A successful delivery does not overcome it.

Required proof: supplier payout is impossible before contractual acceptance, becomes eligible after acceptance, releases once, and retries idempotently after a crash.

### 4. P0 for Razorpay — Incoming payment protocol is still incompatible

[inbox_processors.ts:752](/home/virk/Projects/B2B/sablestone-brokerage/src/runtime/inbox_processors.ts:752) requires a string timestamp suitable for `Date.parse`. Native Razorpay webhook timestamps are numeric Unix seconds. At line 765, provider amount is stringified and compared directly with settlement decimal money; no paise-to-rupee conversion occurs.

Local production-handler results:

```
created_at: 1788600000
-> provider occurred_at missing

created_at: "2026-09-05T09:20:00Z"
provider amount: 10000000 paise
instruction gross: 100000 INR
-> funding amount or currency mismatch
```

Outgoing order/checkout corrections do not fix inbound normalization. See [Razorpay payment webhook examples](https://razorpay.com/docs/webhooks/payments/).

Required proof: provider-specific canonical event conversion, tested with unmodified native timestamp/amount payloads, duplicate events, missing required evidence and out-of-order events.

## Additional autonomy and safety defects supported by source

### 5. P0 for Cashfree — Local HELD state is not evidence of provider hold

[settlement_http.ts:336](/home/virk/Projects/B2B/sablestone-brokerage/src/connectors/settlement_http.ts:336) creates/checks the supplier split. The inbox then creates a local payout control marked HELD; this does not independently establish an acceptance-conditional provider hold.

The later eligibility-date release API exists, but Cashfree documents a finite deferred period, after which settlement follows the configured schedule. The API cannot extend beyond its maximum eligibility date. A local dispute/freeze is therefore not sufficient evidence that funds cannot leave the provider after the delay. See [Cashfree deferred settlement](https://www.cashfree.com/docs/payments/split/settlements/delay/vendor-level).

Keep this rail unavailable for the constitutional delivery-conditioned flow unless the exact approved provider arrangement and implemented controls demonstrably hold funds through late delivery and disputes. This is not solved merely by supplying API credentials.

### 6. P0 for an autonomous book — No shared inventory/demand commitment control found

[stage_handlers.ts:511](/home/virk/Projects/B2B/sablestone-brokerage/src/runtime/stage_handlers.ts:511) filters each candidate against the original offer/demand quantity. Multiple compatible pairs can progress independently. The production protection/funding path does not reserve or consume lot availability or aggregate committed quantity across competing trades.

Thus two 80 MT trades can each regard the same 100 MT lot as sufficient. An individual supplier may reject one, but that is not software-enforced allocation safety. Buyer demand can likewise be matched into multiple independently executable orders.

The schema contains `inventory_refreshes`, but no production writer/scheduler using that table was found. Freshness expiry is not the same as automatically requesting and ingesting inventory reconfirmation indefinitely.

Required proof: concurrent commitment cannot exceed verified stock or buyer-authorized quantity; cancellation releases capacity; settlement consumes it; ongoing supplier reconfirmation wakes the appropriate candidates. This is a source-level concurrency finding, not an executed two-funded-trades test.

### 7. P0 for the recurring business — First-order-to-standing-order wiring is incomplete

[inbox_processors.ts:326](/home/virk/Projects/B2B/sablestone-brokerage/src/runtime/inbox_processors.ts:326) persists ordinary inbound buyer demand with `standing=false`.

[commands.ts:587](/home/virk/Projects/B2B/sablestone-brokerage/src/runtime/commands.ts:587) requires the demand to already have `standing=true` to authorize a standing order. The portal advertises standing authorization after settlement, but the normal one-off demand cannot pass that condition.

There is also a timing break. [RecurringDemandWorkflow](/home/virk/Projects/B2B/sablestone-brokerage/src/workflows/production.ts:30) checks for a mandate immediately after reconciliation and exits if no accepted schedule exists. Authorizing later inserts a mandate but emits no wake-up event, and the supervisor has no standing-authorization route.

The long-cadence timer and reserved/committed renewal internals can be correct while this entry path remains broken.

Required proof: buyer completes an ordinary trade, waits until after reconciliation/workflow completion, authorizes a standing order through the portal, and a fresh due cycle starts without database edits or workflow restarts by an operator.

### 8. P0 for hands-free recovery — Started workflows can still strand work

[production.ts:20](/home/virk/Projects/B2B/sablestone-brokerage/src/workflows/production.ts:20) caps activity attempts at five and schedule-to-close at ten minutes. [supervisor.ts:90](/home/virk/Projects/B2B/sablestone-brokerage/src/runtime/supervisor.ts:90) starts workflows without a workflow retry policy or a failed-workflow reconciliation mechanism.

Outbox redrive covers failure to start a workflow. It does not automatically restart a workflow that already started, exhausted retries during an infrastructure outage and failed after the outbox was marked published.

[document_jobs.ts:187](/home/virk/Projects/B2B/sablestone-brokerage/src/runtime/document_jobs.ts:187) and [enrichment_jobs.ts:133](/home/virk/Projects/B2B/sablestone-brokerage/src/runtime/enrichment_jobs.ts:133) also still contain terminal FAILED paths after repeated errors, without corresponding autonomous claim/redrive paths for those states.

Required proof: prolonged database/provider outage after workflow start, then recovery, results in completion or a policy-valid business termination without manual restart. Separate invalid work from valid work suffering infrastructure failure.

### 9. P1 — Action reminders reuse first-send uniqueness keys

[counterparty_actions.ts:34](/home/virk/Projects/B2B/sablestone-brokerage/src/runtime/counterparty_actions.ts:34) schedules repeat notifications but reuses `action:<id>` for the communication external-event ID and outbound idempotency key. Those keys are unique. After the first send, the next reminder's ordinary INSERT conflicts rather than creating a new reminder.

Action and notification creation are also separate statements, so interruption between them can leave an action without a notification; the later ON CONFLICT path does not repair that gap.

Required proof: first notification and two later reminder occurrences create distinct sends while retries of each occurrence remain idempotent; crash between action and notification cannot strand the action.

### 10. P0 for exception completion — Supplier-winning dispute does not resume the full path

[inbox_processors.ts:1131](/home/virk/Projects/B2B/sablestone-brokerage/src/runtime/inbox_processors.ts:1131) changes a disputed trade to ACCEPTED and resets its payout state, but does not emit `TRADE_ACCEPTED`. It also does not create a provider-resolution release authorization that substitutes for buyer delivery acceptance.

The supplier-payout claim requires a `delivery_acceptances` row. In the usual dispute scenario, the buyer has not accepted delivery. Consequently, fixing the SQL alone still does not make the supplier-winning resolution payable or launch reconciliation/recurrence.

The handler excludes already SETTLED/RECURRING trades from its FAILED/REVERSED state branch. No automatic corrective accounting path for a late reversal was found in that production branch. Domain ledger reversal tests do not establish production wiring.

Required proof: supplier-winning resolution releases under provider authority and starts the closing workflow; buyer-winning resolution proves actual refund; late financial reversal creates exact corrective postings and appropriate restrictions.

### 11. P1/P0 at scale — Provider ledger aggregation is narrower than accounting tables

[inbox_processors.ts:793](/home/virk/Projects/B2B/sablestone-brokerage/src/runtime/inbox_processors.ts:793) requires every disbursement event amount to equal the entire instruction's SableStone entitlement and resolves one instruction by its provider reference.

The newer bank allocation machinery can prevent double allocation of a shared bank receipt. That does not itself normalize native provider batches, partial disbursements, deductions and reversals into the per-trade ledger entries it needs. Multiple partial disbursement events for one fee currently fail this exact-amount gate.

Required proof: native provider batch/report ingestion yields an exact many-trade allocation, source residual capacity is preserved, partial fee disbursements sum correctly, and provider/bank/invoice/tax totals reconcile including permitted adjustments. Alternatively restrict the enabled rail to a proven simpler payout contract before quoting.

### 12. P0 for autonomous onboarding — Per-counterparty payment onboarding is not implemented end-to-end

[provider_parties.ts:272](/home/virk/Projects/B2B/sablestone-brokerage/src/runtime/provider_parties.ts:272) requires existing verified provider-party mappings. The provisioning surface at [server.ts:599](/home/virk/Projects/B2B/sablestone-brokerage/src/api/server.ts:599) is SYSTEM-only and registers references supplied by the caller. No production workflow was found that onboards every newly discovered supplier/vendor/linked account with the payment provider and registers the result.

IdP invitations do not create payment-provider accounts. One-time SableStone API keys do not satisfy this per-new-counterparty dependency.

The shipment form now includes upload and transit/delivery actions, closing the previous missing-form issue. However, its carrier selector depends on verified `carrier_profiles`; only reads and the migration were found, not a production onboarding/refresh writer. Document the exact automated source for this registry instead of requiring internal IDs/database inserts.

### 13. P1 — Rediscovery can downgrade qualified counterparties permanently

[discovery_service.ts:389](/home/virk/Projects/B2B/sablestone-brokerage/src/runtime/discovery_service.ts:389) replaces a same-country jurisdiction record's VERIFIED state with SOURCE_STATED on rediscovery.

Its KYB enqueue at line 438 skips an organization if any KYB job already exists, including a completed prior job. Repeated discovery can therefore remove the verified route fact without scheduling renewed verification.

Required proof: rediscovery preserves current stronger evidence or triggers re-verification, including expiration, country conflict, and a previously completed KYB job. Discovery must not degrade a working book into an indefinitely waiting book.

### 14. P0 for clean deployment — Build relies on undeclared global TypeScript

[package.json:9](/home/virk/Projects/B2B/sablestone-brokerage/package.json:9) runs `tsc`, but root dependency manifests do not install TypeScript. [Containerfile.api:5](/home/virk/Projects/B2B/sablestone-brokerage/Containerfile.api:5) installs only root dependencies before building.

The developer machine has a global compiler, which explains successful local builds. Removing that global tool from PATH while keeping the repository/dependencies yielded `sh: 1: tsc: not found`. A container build was not executed during this audit; the manifest/toolchain defect was reproduced separately.

Required proof: a clean, declared-toolchain API and worker image builds and starts without borrowing global developer tools.

## Why green verification did not settle this

[full-simulation.mjs:9](/home/virk/Projects/B2B/sablestone-brokerage/scripts/full-simulation.mjs:9) executes separate domain contract scripts, then walks a fixed list of states using synthetic evidence booleans. It prints `manual_steps=0`; it does not measure founder interventions in one connected production transaction.

[verify-launch-engine.mjs:5](/home/virk/Projects/B2B/sablestone-brokerage/scripts/verify-launch-engine.mjs:5) records local compile/build/tests/contracts/signature verification. Its command list does not start and drive a combined PostgreSQL/Temporal/storage/provider/portal journey.

The signature is meaningful evidence of the recorded checks. Their scope is insufficient. The real-database errors above demonstrate that directly. Reintroducing GitHub Actions is neither requested nor necessary: a reproducible local or alternative CI integration harness can supply the missing proof.

## Required software exit test

After correcting these findings, run the production API, worker, PostgreSQL, Temporal and object storage together with controlled external-provider simulators using native schemas. Exercise one connected journey, not separately passing state functions:

```
new counterparty -> qualification -> provider onboarding -> first outreach
-> offer/demand -> economics -> negotiation -> exact acceptances
-> real instruction persistence -> native funding event -> fee lock
-> identity release -> contract -> shipment uploads -> acceptance
-> supplier release -> brokerage disbursement -> bank allocation
-> invoice/tax reconciliation -> delayed standing authorization
-> second order with new economics and a new entitlement
```

Add concurrent stock/demand allocation, prolonged outages, reminders, supplier/buyer dispute results, partial/batched payouts, late reversal, rediscovery and credential/evidence expiry. Assert persisted money/state/outbox facts after restarts and prove no manual repair is necessary.

Then test selected provider sandboxes and deployed infrastructure. Native-format fakes prove internal behavior; they cannot prove actual provider acceptance, custody treatment, settlement behavior or bank reconciliation.

## External gates remain separate

This verdict does not depend on marking incorporation, banking, credentials or hosting missing. Even assuming those are ready, the software findings above remain.

Written exact-use-case provider approval, legal/tax/privacy review, actual restore proof and a bounded genuine trade ending in reconciled bank credit are additional activation requirements. None were fabricated or satisfied by this audit.

This is a substantive audit across the production lifecycle, not a mathematical guarantee that no further bug exists. The correct next milestone is executable integrated evidence, not another unsupported percentage-complete claim.
